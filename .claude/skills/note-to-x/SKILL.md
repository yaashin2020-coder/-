# note → X シェア

noteで公開した記事を、Xの投稿文に変換するためのスキル。

## 前提となるワークフロー

```
[note365-auto-post]  記事の下書きを作る（自動）
        ↓
[ユーザー]           下書きを確認し、自分の手でnoteに公開する
        ↓
[ユーザー]           このセッションに「投稿した」と入力する
        ↓
[このスキル]         X用の投稿文＋ワンタップリンクを作る
        ↓
[ユーザー]           リンクをタップしてXへ送信する
```

**自動で外部に何かを出す工程はひとつもない。** note への公開も X への送信も
人間が押す。このスキルの担当は「投稿文を作る」ところまで。

「投稿した」という報告は **noteへの公開が済んだ合図**であって、
Xへ投稿してよいという指示ではない。投稿文を見せて確認を取る。

## 手順

### 1. 記事の内容を受け取る

**まずRSSを試す。** 最新記事のタイトル・URL・本文がすべて入っているので、
これが取れればユーザーは「投稿した」の一言だけでよく、URLも要点も貼らずに済む。

```bash
python3 scripts/fetch_note_latest.py --user long_whale5827
```

ユーザー名は `references/config.md` の `note_username`。出力はJSONで
`title` / `url` / `published` / `body` が入る。

#### RSSが取れたとき

**必ず、どの記事を使うかをタイトルと公開日時で示してから投稿文を作る。**

> 最新記事はこれで合ってますか？
> 「〈タイトル〉」（〈公開日時〉）

出力に `warning` が入っていたら**そのまま黙って進めない**。RSSの反映が
遅れていて、**今公開した記事ではなく1つ前の記事**が最新として返っている
可能性がある。これに気づかず進むと、実在するURLに別記事の要約が付く。
警告が出たら数分待って取り直すか、ユーザーにURLを聞く。

#### RSSが取れないとき

`note.com` が許可リストに入っていないと `Tunnel connection failed: 403` で
落ちる（2026-07-25時点のこのenvironmentがその状態）。その場合の代替：

1. `references/config.md` の `draft_source` に下書きの保存先があり、そこから
   読める場合 → 読んで使う。Google Drive / Notion はコネクタ経由で到達できる。
   **どの下書きを使ったかを明示して確認を取る。**
2. ユーザーがメッセージ内に本文・要点を貼っている場合 → それを使う。
3. どちらもない場合 → 一度にまとめて聞く：

> 記事のURLと、要点を2〜3行貼ってください。音声入力でも大丈夫です。

この経路では**記事URLが必須**。公開後にしか確定せず、こちらからは知りようがない。
恒久的に貼る手間をなくしたいなら `note.com` の許可が要ると伝える
（手順は `references/setup.md`）。

#### 共通

- **憶測で記事内容を書かない。** 手元にない情報を投稿文に混ぜるのは厳禁。
- 記事が短くて要点が薄いときは、盛らずにそのまま短い投稿文にする。
- `config.md` の投稿履歴に同じURLがあれば、重複投稿になると伝えて確認する。

**ユーザーはスマホから使っていることが多い。** その前提で：

- 質問は一度にまとめる。何往復もさせない。
- 返答は短くする。長い前置き・手順の再説明をしない。
- ワンタップリンクは**メッセージの最後**に置く。タップしやすい。
- 本文まるごとでなく箇条書きで十分だと伝える。スマホで打つ量が大きく減る。

スマホ運用の詳しい手順は `references/mobile-flow.md`。

### 2. 投稿文を作る

`references/style.md` にユーザーの好みの型がある場合はそれに従う。ない場合の既定：

```
<記事の要点を1〜2文。記事に実際に書かれている内容だけ>

<noteのURL>

#ハッシュタグ #ハッシュタグ
```

制約：

- **280文字**（半角換算。日本語は1文字=2カウント相当ではなく、Xの日本語カウントは
  1文字=2重み → 実質全角140文字が上限）。`scripts/post_to_x.py --count` で正確に測れる。
- **URLは何文字でも23文字分**として計算される（t.co短縮のため）。
- ハッシュタグは2〜3個まで。多いとスパムに見える。
- 記事タイトルをそのまま貼るだけにしない。読んだ人が「読みたい」と思う一文にする。
- 煽り・誇張（「衝撃の」「99%の人が知らない」等）は入れない。

長い記事は**スレッド**にしてもよい。その場合は1投目に要点とURL、2投目以降に補足。

### 3. ワンタップ投稿リンクを渡す（既定）

`references/config.md` の `mode` が `intent`（既定）のとき、**私は投稿しない。**
投稿文とリンクを作り、送信はユーザーに委ねる。

```bash
python3 scripts/post_to_x.py --intent --text "投稿文"
```

出力される `https://x.com/intent/post?text=...` を、投稿文の全文と一緒に返す。
リンクを開くと本文が入った状態のXの投稿画面になり、ユーザーが送信ボタンを押す。
**認証情報もネットワーク許可も不要。**

返し方の型：

> 投稿文（◯◯/280文字）:
>
> ```
> <投稿文の全文>
> ```
>
> ワンタップ投稿: <リンク>
>
> 直したいところがあれば言ってください。

文字数超過はスクリプトが弾く（exit 1）ので、その場合は短くして測り直す。
投稿文を修正したら**リンクも作り直す**。古いリンクを渡さない。

スレッドにする場合は `--text` を複数回渡す。ただしintentモードでは投稿ごとに
別リンクになり、返信として繋がらない。スレッドが要るなら `auto` モードを勧める。

### 3'. 直接投稿する（`mode: auto` のときだけ）

```bash
python3 scripts/post_to_x.py --text "投稿文"                # 単発
python3 scripts/post_to_x.py --text "1投目" --text "2投目"  # スレッド
```

このモードでも、**投稿前に必ず本文案を見せて明示的なOKを取る。**
Xへの投稿は取り消しづらい外向きの行為で、勝手に送信しない。

セットアップ（APIキー取得・ネットワーク許可）の手順は `references/setup.md` にある。

## やらないこと

- ユーザーの確認なしに投稿する
- 「投稿した」の報告を、Xへ投稿してよいという指示だと解釈する
  （それはnoteへの公開が済んだという報告にすぎない）
- noteの記事を代わりに公開する。公開はユーザーの担当
- 記事に書かれていない内容を投稿文に足す
- 取得できなかった記事の内容を推測で書く
- どの下書きを使ったか示さずに投稿文を作る（別記事の取り違えを防ぐ）
- 同じ記事を重複投稿する（`config.md` の投稿履歴を見る／不明なら聞く）
